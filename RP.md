Введение
Подготовка к основному государственному экзамену (ОГЭ) и единому государственному экзамену (ЕГЭ) по математике и информатике — устойчивая массовая потребность школьников и их родителей. Её закрывают три разных типа сервисов. Открытые порталы с банками заданий (например, «Решу ЕГЭ») дают много тренировочного материала, но не ведут ученика по индивидуальному плану. Онлайн-школы продают курсы целиком. Маркетплейсы репетиторов (например, Preply) помогают найти преподавателя, но удерживают с него значительную комиссию — по открытым условиям Preply от 18 до 33 % стоимости урока и 100 % стоимости пробного. Частный репетитор при этом по-прежнему ведёт расписание в календаре, домашние задания рассылает в мессенджерах, а оплаты записывает в таблицу.
В работе предлагается объединить эти потребности в одной веб-платформе PeopleMayLearn. Для массового ученика она бесплатна: банк задач, привязанных к темам и номерам заданий КИМ, мгновенная автопроверка ответов, прогресс по темам и игровые механики (очки опыта, серии дней, рейтинг). Платными становятся расширенные возможности: Premium-подписка для ученика и тарифы для репетиторов, которым платформа даёт расписание, домашние задания, учёт оплат и каталог для привлечения учеников. Дополнительный доход приносит небольшая комиссия с оплат занятий, проходящих через платформу.
Объектом курсовой работы является процесс подготовки школьников к экзаменам по математике и информатике и сопровождающие его процессы организации занятий, расчётов и монетизации сервиса. 
Предметом работы является модель данных информационной системы «PeopleMayLearn», обеспечивающая хранение и обработку этих данных, включая правила тарификации.
Цель работы — спроектировать модель данных системы «PeopleMayLearn», реализовать на её основе базу данных и показать её работу на демонстрационных сценариях.
Для достижения цели необходимо решить следующие задачи:
    • описать предметную область, сформулировать требования и модель монетизации, выполнить обзор аналогов (разделы 1–4);
    • построить концептуальную схему данных (раздел 5) и подготовить наброски интерфейса (раздел 6);
    • обосновать выбор системы управления базами данных (раздел 7.1);
    • преобразовать концептуальную схему в логическую (раздел 7.2) и физическую (раздел 7.3);
    • реализовать базу данных, наполнить её тестовыми данными и продемонстрировать работу бизнес-правил на сценариях (раздел 7.4).
Работа состоит из введения, разделов технического задания (разделы 1-6) и исследовательской части (раздел 7), в которой выполнено проектирование и реализация базы данных.
1. Общие сведения
Наименование системы: PeopleMayLearn — онлайн-платформа подготовки к ОГЭ и ЕГЭ по математике и информатике с банком задач, автоматической проверкой ответов и кабинетом репетитора.
Цель разработки: создание веб-системы, которая привлекает массового пользователя бесплатным тренажёром задач и зарабатывает на платных подписках и комиссии с занятий репетиторов.
Назначение курсовой работы: спроектировать модель данных системы (концептуальную, логическую и физическую) и реализовать на её основе базу данных и прикладной слой с типовыми запросами.
2. Описание предметной области
2.1. Введение
Подготовка к экзаменам включает три связанных процесса. Первый — самостоятельная тренировка: ученик решает задачи, получает мгновенную обратную связь и видит свои слабые места. Второй — индивидуальные занятия с репетитором: диагностика, учебный план, занятия, домашние задания. Третий — деньги: оплаты занятий и абонементов, долги, а у самой платформы — подписки и комиссия. Для каждого процесса сегодня используются разрозненные инструменты, из-за чего история занятий и прогресс ученика трудно отследить, а репетитор тратит время на рутину.
2.2. Субъекты и роли
    • Гость. Просматривает публичный каталог репетиторов, тарифы и часть задач, оставляет заявку на консультацию.
    • Ученик. Решает задачи в тренажёре, видит прогресс, очки опыта и рейтинг; получает занятия и домашние задания от репетитора. Бесплатный ученик имеет доступ к открытой части каталога; ученик с Premium-подпиской — ко всем задачам, разборам и материалам.
    • Репетитор. Ведёт учеников, расписание, абонементы и оплаты, выдаёт домашние задания, создаёт свои задачи и материалы, получает заявки из каталога. Возможности зависят от тарифа: без подписки — до 3 учеников, Start — до 10, Pro — без ограничений.
    • Администратор платформы. Управляет каталогом задач и тарифами, обрабатывает общие заявки, контролирует доходы платформы.
2.3. Основные процессы и сущности
Каталог задач и тренажёр. Задача принадлежит предмету, относится к одной или нескольким темам, имеет тип экзамена (ОГЭ, ЕГЭ или школьная программа), номер задания КИМ, сложность, эталонный ответ и разбор решения. Часть задач помечена как Premium. Ответ ученика сохраняется как попытка и проверяется автоматически.
Учебный план и прогресс
Темы образуют дерево «раздел — подраздел». Для каждого ученика по каждой теме хранятся статус («Не начато», «В изучении», «Освоено») и процент освоения; по ним строятся список «слабых» тем и рекомендации задач.
Вовлечение
За каждую попытку ученик получает очки опыта; ежедневная активность образует серию дней подряд; по очкам строится рейтинг.
Занятия и домашние задания
Занятие проводится репетитором для ученика в определённое время, на нём разбираются одна или несколько тем. По итогам может быть выдано домашнее задание — подборка задач каталога. Ответы на задачи задания фиксируются теми же попытками.
Расчёты репетитора с учеником
Занятие оплачивается разово или списывается с абонемента (пакета занятий). Баланс ученика равен сумме внесённых платежей минус стоимость проведённых занятий; отрицательный баланс — задолженность.
Доходы платформы
Платформа зарабатывает тремя способами: Premium-подписки учеников, подписки репетиторов (тарифы Start и Pro) и комиссия с оплат занятий и абонементов, проходящих через платформу (таблица 1).

2.4. Бизнес-правила
    • Автопроверка. Числовой ответ сравнивается с эталонным как число (запятая и точка равнозначны), строковый — без учёта регистра и пробелов по краям.
    • Прогресс по теме = доля верных попыток по задачам темы. Тема получает статус «Освоено» при не менее чем 5 попытках и доле верных от 80 %, иначе «В изучении».
    • Очки опыта: +10 за верный ответ, +1 за неверный. 
    • Серия дней: решение вчера продлевает серию, повторное решение в тот же день серию не меняет, пропуск дня начинает серию с единицы.
    • Жизненный цикл занятия: «Запланировано» → «Проводится» → «Завершено» → «Рассчитано» → «Оплачено»; из «Запланировано» возможна отмена. Перенос занятия — изменение даты, пока оно запланировано. Прочие переходы запрещены.
    • Расчёт занятия: если у ученика есть оплаченный действующий абонемент с остатком, занятие списывается с него, а стоимость занятия фиксируется как цена абонемента, делённая на число занятий; иначе занятие остаётся к оплате как разовое.
    • Пропуски: пропущенное занятие оплачивается, если репетитор не обнулил его стоимость (пересчёт по договорённости).
    • Баланс = оплаченные платежи за занятия и абонементы − стоимость занятий со статусами «Завершено», «Рассчитано», «Оплачено».
    • Лимиты тарифа: репетитор без активной подписки может иметь до 3 активных учеников; подписка Start поднимает лимит до 10, Pro снимает его.
    • Доход платформы: с платежа-подписки — вся сумма; с платежа за занятие или абонемент — 10 %. Сумма фиксируется в момент платежа, поэтому смена ставки в будущем не меняет историю.
    • Подписка создаётся в статусе «Ожидает оплаты» и становится активной после успешной оплаты; у пользователя может быть не более одной активной подписки.
2.5. Взаимосвязи
    • Один пользователь имеет не более одного профиля репетитора и не более одного профиля ученика; репетитор может вести много учеников, ученик — заниматься у многих репетиторов.
    • Предмет содержит много тем (с вложенными подтемами); задача относится к нескольким темам и наоборот (связь «многие ко многим»); к теме привязаны материалы.
    • Репетитор проводит много занятий, ученик посещает много занятий; на занятии разбираются несколько тем (связь «многие ко многим»).
    • Домашнее задание состоит из многих задач, а задача входит в разные задания (связь «многие ко многим»); ответы учеников — попытки — привязаны к ученику, задаче и, при необходимости, к заданию.
    • Прогресс — связь «ученик — тема» с атрибутами статуса и процента освоения.
    • Платёж относится ровно к одному объекту: подписке, абонементу или занятию; подписка относится к тарифу.
3. Описание требований к системе
3.1. Пользовательские истории (User Stories)
    • Как ученик, я хочу сразу после ответа видеть, верно ли решено, чтобы понимать ошибки без ожидания проверки.
    • Как ученик, я хочу видеть «слабые» темы и получать задачи именно по ним, чтобы готовиться эффективнее.
    • Как ученик, я хочу копить очки и серию дней подряд, чтобы заниматься регулярно.
    • Как ученик, я хочу оформить Premium и получить доступ ко всем задачам и разборам.
    • Как репетитор, я хочу вести расписание и видеть баланс и долги каждого ученика, чтобы не вести учёт в таблице.
    • Как репетитор, я хочу выдавать домашнее задание из каталога и видеть результаты автопроверки.
    • Как репетитор, я хочу размещать анкету в каталоге и получать заявки новых учеников.
    • Как владелец платформы, я хочу видеть доход по месяцам и по видам платежей.
3.2. Функциональные требования
    • Аккаунты и тарифы: регистрация по e-mail и паролю, роли, профили; выбор и оплата тарифа, автоматическое применение лимитов и доступа.
    • Каталог и тренажёр: фильтры по предмету, экзамену, номеру КИМ, сложности, теме; ввод ответа и автопроверка; разбор решения.
    • Прогресс и вовлечение: дерево тем с процентами, «слабые» темы, очки опыта, серия дней, рейтинг.
    • Занятия: календарь, перенос и отмена, жизненный цикл по статусам, присутствие, темы занятия.
    • Домашние задания: подборка задач, выдача ученику, срок, статус, результаты.
    • Расчёты и финансы: абонементы, платежи, баланс и долги ученика, доход платформы.
    • Каталог репетиторов и заявки: публичная анкета, форма заявки на консультацию, статусы заявок.
3.3. Нефункциональные требования
    • Адаптивный веб-интерфейс: основной сценарий ученика — со смартфона.
    • Разграничение прав: ученик видит только свои данные; репетитор — данные своих учеников; гость — публичную часть.
    • Целостность данных обеспечивается на уровне СУБД: ограничения CHECK, внешние ключи, перечисления, триггеры (раздел 7.3).
    • Безопасность: пароли хранятся только в виде стойких хэшей (bcrypt или Argon2); защита от SQL-инъекций (параметризованные запросы), XSS и CSRF; обмен по HTTPS.
    • Платежи проводятся через внешний платёжный шлюз; данные банковских карт в базе не хранятся — только сумма, статус и ссылка на объект оплаты. В макете оплата имитируется.
    • Резервное копирование базы не реже одного раза в сутки.

7. Исследовательская часть
7.1. Обоснование выбора СУБД
Данные «PeopleMayLearn» хорошо структурированы и тесно связаны: пользователь, профили, задачи и темы, занятия, домашние задания, попытки, подписки и платежи (раздел 5). Основные операции — выборки с соединением таблиц и агрегацией (прогресс по теме, рейтинг, баланс ученика, доход по месяцам). Платёжные операции требуют транзакционной целостности: подписка не должна активироваться без записи об оплате, а занятие не должно списываться с абонемента дважды. Поэтому выбрана реляционная модель. Нереляционные хранилища не дают встроенного контроля ссылочной целостности и неудобны для агрегирующих запросов, поэтому не рассматривались.
Из реляционных СУБД сравнивались PostgreSQL, MySQL, Microsoft SQL Server и SQLite по критериям, существенным для проектируемой системы (таблица 4).

Для «PeopleMayLearn» решающими оказались следующие свойства PostgreSQL:
    • Контроль целостности на уровне СУБД. Статусы занятий, платежей и подписок ограничены перечислениями, суммы и цены — условиями CHECK, связи — составными внешними ключами (например, занятие возможно только между связанными репетитором и учеником).
    • Бизнес-правила в самой базе данных. Автопроверка ответа, пересчёт прогресса и очков, контроль статусов занятия, лимит учеников по тарифу и расчёт комиссии реализованы функциями и триггерами PL/pgSQL, поэтому действуют одинаково для веб-интерфейса, мобильного клиента и административных скриптов.
    • Массовая нагрузка. Тренажёр рассчитан на много одновременных пользователей: модель MVCC позволяет читать каталог и записывать попытки без взаимных блокировок.
    • Частичные индексы. Каталог опубликованных задач, активные подписки и оплаченные платежи — подмножества таблиц; частичные индексы компактнее и быстрее. Частичный уникальный индекс гарантирует не более одной активной подписки у пользователя; в MySQL такого нет.
    • Стоимость и переносимость. СУБД бесплатна и работает на всех основных платформах, что важно для стартапа с ограниченным бюджетом.
Вывод: для реализации системы выбрана реляционная СУБД PostgreSQL версии 16.

7.2. Логическая схема базы данных
Логическая схема построена преобразованием концептуальной модели в реляционную. Применялись правила: каждая сущность становится отношением; идентификатор — первичным ключом; связь «один ко многим» — внешним ключом на стороне «многие»; связь «многие ко многим» разрешается ассоциативным отношением с составным первичным ключом; специализация («Репетитор» и «Ученик» как виды «Пользователя») — отношением-профилем, первичный ключ которого одновременно является внешним ключом на «Пользователя».

При переходе от концептуальной к логической схеме внесены следующие решения:
    • Ассоциативные отношения task_topic, lesson_topic, homework_task, progress и tutor_student разрешают пять связей «многие ко многим»; у progress и tutor_student, помимо ключа, есть собственные атрибуты (статус и процент освоения; цена занятия).
    • Платёж относится ровно к одному объекту — подписке, абонементу или занятию. Это реализовано тремя необязательными внешними ключами и ограничением, требующим, чтобы заполнен был ровно один из них, согласованный с видом платежа. Альтернатива — три отдельные таблицы платежей — отвергнута: усложняла бы отчёт о доходах.
    • Составные внешние ключи. Занятие и абонемент ссылаются на пару (репетитор, ученик) из tutor_student, поэтому занятие между не связанными пользователями невозможно. Попытка ссылается на пары (задание, задача) и (задание, ученик): ответ на домашнее задание можно дать только на входящую в него задачу и только тому ученику, кому оно выдано.
    • Номер КИМ хранится в задаче вместе с типом экзамена: у школьной программы номера нет, у ОГЭ и ЕГЭ он обязателен.
Нормализация. Все атрибуты атомарны (первая нормальная форма). Составной первичный ключ имеют только ассоциативные отношения, и их неключевые атрибуты зависят от ключа целиком (вторая нормальная форма). Неключевые атрибуты зависят только от ключа: цена тарифа хранится в subscription_plan, а не в подписке; название темы — в topic, а не в попытке (третья нормальная форма). Осознанно допущены следующие избыточные (вычисляемые или фиксируемые) значения:
    • student_profile.xp, streak_days, last_active_date — агрегаты по попыткам; хранятся для быстрого вывода шапки и рейтинга, поддерживаются триггером;
    • progress.mastery_percent и status — производные от попыток; пересчитываются триггером при каждой попытке;
    • payment.platform_fee — доход платформы фиксируется на момент платежа, чтобы смена ставки комиссии не меняла историю;
    • lesson.price — стоимость занятия фиксируется, чтобы изменение цены в связи «репетитор — ученик» не пересчитывало прошлые занятия;
    • task.subject_id — предмет можно получить через тему, но прямая ссылка ускоряет фильтрацию каталога.

CREATE FUNCTION fn_attempt_check() RETURNS trigger AS $$
DECLARE
    t task%ROWTYPE;
BEGIN
    SELECT * INTO t FROM task WHERE task_id = NEW.task_id;
    IF t.answer_type = 'number' THEN
        BEGIN
            NEW.is_correct := replace(trim(NEW.answer), ',', '.')::numeric
                            = replace(trim(t.correct_answer), ',', '.')::numeric;
        EXCEPTION WHEN invalid_text_representation OR numeric_value_out_of_range THEN
            NEW.is_correct := false;
        END;
    ELSE
        NEW.is_correct := lower(trim(NEW.answer)) = lower(trim(t.correct_answer));
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql SET search_path = pml;
 
CREATE TRIGGER trg_attempt_check
BEFORE INSERT ON attempt
FOR EACH ROW EXECUTE FUNCTION fn_attempt_check();
 
CREATE FUNCTION fn_lesson_status() RETURNS trigger AS $$
BEGIN
    IF NEW.status = OLD.status THEN
        RETURN NEW;
    END IF;
    IF NOT (   (OLD.status = 'planned'     AND NEW.status IN ('in_progress', 'cancelled'))
            OR (OLD.status = 'in_progress' AND NEW.status = 'completed')
            OR (OLD.status = 'completed'   AND NEW.status = 'calculated')
            OR (OLD.status = 'calculated'  AND NEW.status = 'paid')) THEN
        RAISE EXCEPTION 'Недопустимый переход статуса занятия: % -> %', OLD.status, NEW.status;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql SET search_path = pml;
 
CREATE TRIGGER trg_lesson_status
BEFORE UPDATE OF status ON lesson
FOR EACH ROW EXECUTE FUNCTION fn_lesson_status();
 
CREATE FUNCTION fn_tutor_limit() RETURNS trigger AS $$
DECLARE
    v_limit  integer;
    v_active integer;
BEGIN
    IF NOT NEW.is_active THEN
        RETURN NEW;
    END IF;
 
    SELECT sp.max_students INTO v_limit
      FROM subscription s
      JOIN subscription_plan sp ON sp.plan_id = s.plan_id
     WHERE s.user_id = NEW.tutor_id AND s.status = 'active'
       AND sp.audience = 'tutor' AND s.ends_at >= current_date
     ORDER BY sp.price_month DESC
     LIMIT 1;
    IF NOT FOUND THEN
        v_limit := 3;                      -- бесплатный тариф
    END IF;
 
    SELECT count(*) INTO v_active
      FROM tutor_student WHERE tutor_id = NEW.tutor_id AND is_active;
 
    IF v_limit IS NOT NULL AND v_active >= v_limit THEN
        RAISE EXCEPTION 'Лимит учеников на тарифе исчерпан (%). Оформите подписку репетитора', v_limit;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql SET search_path = pml;
 
CREATE TRIGGER trg_tutor_limit
BEFORE INSERT ON tutor_student
FOR EACH ROW EXECUTE FUNCTION fn_tutor_limit();

SELECT t.title AS topic, k.task_id, k.exam, k.kim_number, k.difficulty, p.mastery_percent
FROM progress p
JOIN topic t       ON t.topic_id = p.topic_id
JOIN task_topic tt ON tt.topic_id = p.topic_id
JOIN task k        ON k.task_id = tt.task_id
WHERE p.student_id = 4 AND p.mastery_percent < 60
  AND NOT EXISTS (SELECT 1 FROM attempt a
                   WHERE a.student_id = p.student_id AND a.task_id = k.task_id AND a.is_correct)
